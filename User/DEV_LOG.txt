一、按键 key.c
================================================================================

-001  按键消抖

    uint32_t now = HAL_GetTick();
    if (now_state != last_raw_level)
    {
        last_raw_level = now_state;
        raw_change_tick = now;                  /* 记录变化时刻 */
    }
    if ((now - raw_change_tick) < KEY_DEBOUNCE_MS)   /* <20ms 视为抖动 */
    {
        return;                                 /* 还没稳定，等下一轮 */
    }

    抖动的处理思路：抖动时不断更新按键状态，直到不再更新并稳定一段时间。

-002  计时基准：必须用真实按下时刻

    该用真实按下时刻作为时间基准，press_tick 只在"松开 -> 按下"的边沿更新。

    【为什么】消抖窗口只能用来"确认状态稳定"，不能同时当"计时起点"。
    否则计时起点会比真实按下晚一个消抖窗口，按住时长被系统性少算，
    结果是按住正好 1.0s 时被误判成短按。

-003  修复之后偏差换了个方向

    press_tick 移到原始变化时刻之后，按住 1.0s 不再被误判成短按。
    但复查时发现偏差没有消掉，只是从负的变成正的：

        按下：记在原始变化时刻        -> 准时
        松手：记在消抖确认时刻        -> 晚 20~30ms

        hold_ms = 松手确认时刻 - 按下时刻 = 真实时长 + 20~30ms（平均 +20）

    两个门槛因此都往下移：

        短按下限   名义 50ms    实际约 30ms
        长按门槛   名义 1000ms  实际约 980ms

    长按偏 2% 手工按键感觉不出来。但短按下限从 50ms 缩到 30ms 有实际影响：
    30~50ms 的触点毛刺原本应该按抖动丢掉，现在刚好够到门槛，被记成一次短按。
    便宜按键的毛刺正好落在这个区间。

-004  松手弹跳会覆盖 press_tick

    比偏差更麻烦的一点：松手时触点也会弹跳，中间可能又短暂闭合一次，
    而刷新 press_tick 的条件只看了"原始电平变成了按下"，没看当前逻辑状态。

        if (now_state == BSP_KEY_PRESSED) { press_tick = now; }

    于是松手弹跳那一次闭合，会把 press_tick 覆盖成松手过程中的某个时刻。
    按住 800ms 后松手，期间有一次弹跳被采样到：

        t=0      按下              press_tick = 0
        t=800    原始断开
        t=810    弹跳又闭合        press_tick = 810        <- 被污染
        t=840    消抖确认松手      hold_ms = 840 - 810 = 30ms -> 小于 50ms，事件丢弃

    结果是一次 800ms 的按键完全没有响应。它是偶发的：10ms 扫描周期配 1~2ms 弹跳，
    弹跳刚好落在采样点上的概率大约一成到两成。

-005  最终改法：只改两行

    第 1 处：刷新 press_tick 时加一个"当前逻辑上还处于松开"的条件，
    松手弹跳就挡在外面了。

        if ((now_state == BSP_KEY_PRESSED) && (key_state_now == BSP_KEY_RELEASED))
        {
            press_tick = now;
        }

    第 2 处：松手时刻不再取 HAL_GetTick()，直接用 raw_change_tick。

        uint32_t hold_ms = raw_change_tick - press_tick;

    【为什么第 2 处能成立】能走到松手判定，说明"连续 20ms 没变化"已经成立，
    raw_change_tick 里存的必然是最后一次变化的时刻，也就是松手那一刻。
    消抖机制本身已经把原始松手时刻保存下来了，不需要再加 release_tick 变量。

    【改完的结果】
        hold_ms 偏差        +10~+30ms   ->  +/-10ms（只剩采样量化）
        短按下限            约 30ms     ->  50ms
        长按门槛            约 980ms    ->  1000ms
        松手弹跳污染        会发生      ->  不会发生
        新增变量            无          ->  0 个

    【剩下的小代价】松手后 20ms 内又按下，key_state_now 还是"已按下"，
    这次重按会被并进上一次按键。两个扫描周期内完成松手再按下，但人要能做到这一点
    就已经是究极生物了，实际上几乎不可能出现碰不到。如果要连这个也避开，
    就再加一个 release_tick 变量，就多两行。

二、LED led.c / led.h

-001  循环计时实现非阻塞闪灯

    计时结束后更新时间戳、再次启动，以实现非阻塞式闪灯。

-002  错误标志用位掩码管理（多错误源互不影响）

    |=  将指定位置置 1

        error_flag  = 0b0000_0001      (ADC 坏了)
        err_mask    = 0b0000_0100      (要置 MPU 位)
                | 或运算
        ------------------------------------
        error_flag  = 0b0000_0101      (ADC + MPU 都坏了)
                                  ^       ^
                               保留了   新加的

    &= ~  将指定位置置 0

        err_mask    = 0b0000_0100      要清 MPU
        ~err_mask   = 0b1111_1011      MPU 那一位变 0，其它位全变 1

        error_flag  = 0b0000_0101      (ADC + MPU 都坏)
        ~err_mask   = 0b1111_1011
                & 与运算
        ------------------------------------
        error_flag  = 0b0000_0001      (MPU 那位被清 0，ADC 保住)

    【注意】判断"有没有错"必须写成 error_flag != 0，不能写 == 1。
    否则只有"恰好一位错误（值为 1）"时才会触发，其它错误源都不亮。

-003  冷上电和手动复位的差别：错误位只置不清

    【现象】拔电再插，自检跑完后 LED1 一直 1Hz 闪；按一下复位键，自检后 LED1 常亮。
    功能都正常，OLED 有显示、串口能应答，只有指示灯不一样。

    【两种启动差在哪】

        冷上电（拔电再插）        手动复位（按 NRST）
        3.3V 从 0 上升            3.3V 已经在位
        外设正在内部上电复位      外设早已稳定
        初始化在 t≈5ms 探针       同样 t≈5ms，但外设已 ready
        -> 探针 NAK，初始化失败   -> 探针成功

    MPU6050 从上电到能响应 I2C 大约要 100ms。main.c 里 logic_attitude_init()
    紧跟在 bsp_adc_init() 后面，离上电只有几毫秒，所以冷上电必然探不到。
    复位时芯片已经上电很久，自然一次就过。

    【为什么灯不灭】error_flag 只置不清：

        void logic_led_set_error(uint8_t err_mask)   { error_flag |= err_mask; }
        void logic_led_clear_error(uint8_t err_mask) { ... }    <- 全工程没有调用点

    led.h 里也写着"当前未使用；预留给外设恢复后停止告警的场景"。
    所以只要失败过一次，哪怕后面外设恢复了，这个位也一直留着。

    【另一个坑】MPU 的 5 秒重试写在"仅模式二随动"之后：

        void logic_gimbal_task(void)
        {
            if(app_mode_get() != MODE_FOLLOW) {return ;}          <- 先 return
            if (logic_attitude_is_ok() == 0) { ...5 秒重试... }   <- 走不到
        }

    默认是模式一，重试一次都不跑；模式一又不需要 MPU，于是"设备正常、灯一直闪"。

    【改法】
        1. main.c 的 USER CODE 2 开头加 HAL_Delay(300)，
           给 3.3V 和外设上电复位留时间（手册约 100ms，留 300ms 余量）
        2. 三个初始化成功分支各清一次位：
               attitude.c -> logic_led_clear_error(LED_ERR_MPU6050);
               oled_ui.c  -> logic_led_clear_error(LED_ERR_OLED);
               main.c     -> ADC 成功时 clear(LED_ERR_ADC)
        3. gimbal.c 把 5 秒重试挪到模式判断之前，任何模式都能自愈

    【位值】led.h 里是 1U<<0 / 1U<<1 / 1U<<2：
        LED_ERR_ADC = 0x01    LED_ERR_OLED = 0x02    LED_ERR_MPU6050 = 0x04
    调试时把 error_flag 打到串口，一眼看出是哪个外设出问题。

    【状态】改法已定，待实机复测。

-001  [重点] 踩坑记录：返回值语义写反，导致 AT 一直回 ERR

     【现象】
     串口助手发 AT，回收 ERR；而按代码逻辑 AT 应该回 OK。
     测试环境：只接了 LED、按键、USB-TTL，其它模块都没接。

     排查过程中出现了一连串"每一环单独看都对"的假象：

         串口收到的字节是对的   L=2 V=41 54（就是干净的 "AT"）
         帧成形成了             发一帧 LED3 会翻转
         解析返回值是对的       rc=1
         解析出的命令是对的     cmd = "AT"
         解析出的参数是对的     param = 0xFFFF（无参数）
         反汇编看也没问题       protocol_parse / protocol_handle 都正确

     但结果就是不走 protocol_handle，直接回 ERR。

     【根本原因】
     protocol_parse 的返回值约定原本是「1 = 解析成功、0 = 解析失败」，
     但调用处写成了：

         if (protocol_parse(line, cmd, &param) != 0)
         {
             bsp_uart_send("ERR\r\n");      /* 把"成功"当成"失败"处理了 */
             return;
         }

     protocol_parse 返回 1（成功）时，`!= 0` 成立，于是直接发 ERR 并 return，
     protocol_handle() 永远得不到调用，OK 自然永远发不出来。

     【解决方式】
     把 protocol_parse 的返回值约定改成与工程其它模块一致：

         0 = 解析成功
         1 = 解析失败（空指针 / 空命令 / 命令超长 / 参数非数字 / 参数溢出）

     做法是 6 个 return 语句全部对调，并把调用处改成：

         if (protocol_parse(line, cmd, &param) == 0)   /* 0 才是成功 */
         {
             /* 正常处理 */
         }
         else
         {
             bsp_uart_send("ERR\r\n");                  /* 非 0 才是失败 */
         }

     改完后 AT 立刻回 OK，YAW 90 回 OK，AT 5 回 ERR。

     【体会与教训】
     1) 返回值的"成功/失败"语义，必须和工程里其它模块对齐。
        本工程里原本只有 protocol_parse 是异类：

            bsp_i2c_write_reg / read_reg / is_device_ready   0 成功 / 1 失败
            bsp_adc_init                                      0 成功 / 1 失败
            dev_oled_init                                     0 成功 / 1 错误
            dev_mpu6050_init / read_raw / calibrate           0 成功 / 1 失败
            logic_attitude_calibrate                          0 成功 / 1 失败
            protocol_parse（改之前）                          1 成功 / 0 失败  <- 唯一的异类

        统一成 0 成功之后，这个 bug 从根上就不会再发生。

     2) 排查方法上的教训：
        要分清"被调用的函数"和"调用处怎么解读返回值"。
        我前面查了很久字节内容、ctime 表、strcmp 实现、反汇编，
        全都是被调用者那一侧，而问题出在调用者那一侧的一行判断。
        以后遇到"每一环都对但整体不对"，要优先看"胶水代码"----
        模块之间的判断、传参、返回值解读。

     3) 0 和 1 哪个表示成功，是这类 bug 的高发点。
        尤其本工程里 bsp_uart_read_line 用 0 表示"没有完整行"、
        而 bsp_i2c_* 用 0 表示"成功"，两种语义并存，最容易记反。

     【回归验证清单】
         发 AT         -> OK          无参数成功路径
         发 STATUS     -> OK MODE=1   另一个无参数分支
         发 YAW 90     -> OK          带参数成功路径（和 AT 不是同一条 return）
         发 YAW 999    -> ERR         参数越界
         发 AT 5       -> ERR         无参指令带参数
         发 XXXX       -> ERR         未识别命令
         发 33 字符垃圾 -> ERR         超长帧
         发 100 字符垃圾 -> ERR        超长帧读完再上报
     每发一帧，LED3 都应翻转一次。

-002  解析 "YAW 90" 这类带参数的指令

    先分离字母，再分离数字。
    使用一个标志 read_pos，用 while 循环忽略空格，把标志逐渐向前移，
    到达指定位置则记录开头。
    判断长度是否合规：用末位置 - 初位置得出长度。

-003  将字符串中的数字转化为 int

    取数字值：s[i] - '0'
    将该值交给数字的个位
    取下一位数字时，前面的数字整体 *10，让出个位

-004  [重点] 踩坑记录：静态行缓冲残留，导致"长指令之后的短指令全部 ERR"

     【现象】
     上电后第一帧 AT 正常回 OK。
     但先发一帧 STATUS 之后，再发 AT 就一直回 ERR；
     之后所有短指令都失败，只有复位重启才恢复。

     实测序列（串口助手记录）：

         (1) STATUS  -> OK MODE=1     正常
         (2) AT      -> ERR           [重点] 发过 STATUS 之后 AT 就坏了
         （两次之间隔了十几秒，所以不是时序或干扰问题，是状态残留）

     【排查过程】
     逐项观测都正常，每一环单独看都没问题：

         串口收到的字节      41 54（就是干净的 "AT"）
         长度               len = 2
         protocol_parse     rc = 1（解析成功）
         cmd 前两字节        41 54（"AT"）

     但结果就是回 ERR。
     [重点] 问题的关键：我一直只打印前 2 个字节，
       正好把"残留的脏字节"砍掉了，导致观测窗口太窄、查了很久。

     【根本原因】
     bsp_uart_read_line 里的行缓冲是 static：

         static char line[UART_LINE_MAX_LEN + 1];

     它只在编译时被清零一次，而成帧时只写了缓冲区尾部的终止符：

         line[UART_LINE_MAX_LEN] = '\0';
         /* 没有写 line[len_read] = '\0'; */

     于是上一帧更长指令的残留字节会被带进下一帧：

         发 STATUS（6 字符）后：line = S T A T U S \0 ...
         再发 AT（2 字符）后：  line = A T A T U S \0 ...
                                        ^^^^
                                 line[2..5] 还是上一帧的残留 "ATUS"

     protocol_parse 扫描命令段时是"扫到 '\0' 才停"，
     所以这次的命令变成了：

         cmd = "ATATUS"     ->  len_cmd = 6
         strcmp("ATATUS","AT")     != 0
         strcmp("ATATUS","STATUS") != 0
         ... 全不匹配 -> 落到最后的 else -> 回 ERR

     这也解释了为什么"上电后第一帧是好的"----
     那时 line 全是 0，line[2] 正好就是 '\0'。

     【解决方式】
     在成帧处补一行，保证"本次实际写入的部分"之后紧跟 '\0'：

         line[UART_LINE_MAX_LEN] = '\0';
         line[len_read] = '\0';        /* [重点] 补这一行 */
         strncpy(buf, line, max_len - 1);
         buf[max_len - 1] = '\0';

     一行就够，零开销，语义精确：只终止本次写入的部分。

     为什么不选其它做法：
         - memset(line, 0, sizeof(line)) 每次调用都要清 33 字节，浪费；
           而且治标不治本----真正的问题是"字符串没在当前长度处终止"。
         - 把 line 从 static 改成局部变量更差：
           局部数组在栈上、未必为零，残留问题会更隐蔽。

     【教训】
     1) 用 static 缓冲拼字符串，必须在"本次实际写入的末尾"补 '\0'，
        而不能只保证缓冲区尾部有 '\0'。否则上一帧的残留会被当成数据读进来。
        这类 bug 的特征是"第一次正常、之后全错"，很容易误判成硬件问题。

     2) 诊断打印要覆盖完整数据，别为了输出简洁牺牲信息量。
        这次因为只打了前 2 个字节，正好把"残留的脏字节"砍掉了，
        导致在"字节内容 / 返回值语义 / 反汇编"上反复排查了好几轮。

     3) 和 -001 放在一起看，这两个 bug 叠加时特别难查：
        -001 是"返回值语义写反"（把成功当失败），
        本条的"行缓冲残留字节"又伪装成"解析失败"，
        两者症状都是"回 ERR"，互相掩盖，
        每次修掉一个都以为好了，实际还有一个在等着。

     【回归验证清单】
         (1) AT        -> OK          第一帧
         (2) AT        -> OK          [重点] 第二次发也要 OK（验证残留已修）
         (3) STATUS    -> OK MODE=1
         (4) AT        -> OK          [重点] 长指令之后短指令仍正常
         (5) aT        -> OK          [重点] 小写也要 OK（toupper 生效）
         (6) YAW 90    -> OK          带参数成功路径
         (7) AT        -> OK          再回到短指令

     其中 (2)(4)(7) 是本次修复的直接验收点。

四、OLED dev_oled.c/h
================================================================================

-001  SSD1306 内存结构

    显存结构：SSD1306 内部有 1KB（1024 字节）的显存（GDDRAM），对应 128 * 64 像素。
    这 1KB 被分成了 8 个"页"（Page），每页负责屏幕上垂直方向的 8 个像素，
    即：每页高 8 个像素。

    数据与像素的对应关系：向屏幕发送的每个字节，其 8 个 bit 恰好对应垂直方向的
    8 个像素。LSB（最低位）在上，MSB（最高位）在下。

-002  I2C 通信协议

    每次通信，STM32 都会按固定格式发送数据。

        发送地址：0x3C << 1（即 0x78），因为 HAL 库需要 8 位地址。
        发送控制字节：
            发送"命令"时，控制字节为 0x00。
            发送"显示数据"时，控制字节为 0x40。

-003  I2C 地址：为什么必须左移一位

    I2C 地址字节是"7 位从机地址 + 1 位读写位"，
    而 STM32 HAL 库约定传入的 DevAddress 必须是已左移 1 位的 8 位地址，
    最低位留给读写位。

    OLED 手册给的 0x3C 是 7 位地址，所以必须写成 (0x3C << 1) = 0x78，
    HAL 才能把高 7 位正确放到 SADD，并在读/写时自动处理最低位。
    若直接传 0x3C，HAL 会误当成 0x1E，导致寻址错误。

    （MPU6050 同理：7 位地址 0x68，HAL 要传 0xD0。）

-004  Font8x16 字模数组的生成方式

    可以通过软件 PCtoLCD2002 生成。
    模式：选择"字符模式"。
    选项：
        点阵格式：阴码
        取模方式：列行式
        取模走向：逆向（低位在前）
    生成：输入需要的字符，点"生成字模"，复制生成的 C 语言数组即可。

-005  字符定位

    每个字符宽 8 像素，所以下一个字符的 x 要加 8；
    一行显示不下时，y 要加 16（如果字体高 16）。

-006  0xB0 是"设置页地址"命令的基址。

-007  命令速查表

    命令                        含义
    ------------------------------------------------------------------
    0xB0 + page                 设置页地址（page = 0~7）
    0x00 | (x & 0x0F)           设置列地址低 4 位
    0x10 | ((x >> 4) & 0x0F)    设置列地址高 4 位
    0x40                        设置显示起始行（通常 0）
    0x8D + 0x14                 使能电荷泵（OLED 必须开）
    0xAF                        打开显示
    0xAE                        关闭显示

-008  x & 0x0F 做了什么

    0000 1111 做与运算，高 4 位被抹掉，低 4 位留下来。

    假设 x 是一个 8 位数据，比如 x = 0x25：

        x        = 0x25 = 0010 0101
        0x0F     =        0000 1111
        --------------------------------
        x & 0x0F =        0000 0101 = 0x05

    高 4 位 0010 与 0000 相与 -> 全变成 0
    低 4 位 0101 与 1111 相与 -> 原样保留
    结果 0x05 就是 x 的低 4 位。

-009  页寻址模式下的定位操作

    页地址用一条命令设置；
    列地址拆成高低 4 位、用两条命令设置。
    之后写入的显示数据会从这个位置开始，逐列存放。

    ===== 这是页寻址模式下每次写入前必须做的定位操作 =====

-010  低 4 位的命令以 0x00 打头，后面接低 4 位数据；
      高 4 位的命令以 0x10 打头，后面接高 4 位数据。

-012  逐字节发送 vs 整页合并：OLED 刷新把主循环吃掉了

    【数字】一个字符 22 次 I2C 传输：

        上页：页地址 + 列低 4 位 + 列高 4 位 + 8 个数据字节 = 11 次
        下页：同样 11 次
        合计 22 次/字符

    一行 16 字符 = 352 次；四行 = 1408 次。
    按 400kHz、单次约 90us 估算，一次刷新约 127ms，比 100ms 的刷新周期还长。

    【和 -011 的关系】-011 里记的是把一页的 8 个数据字节合并成 9 字节，
    能降到 4 次/字符；这里再往前一步，整行 128 字节一次发，降到 8 次/行。

    【后果】app_task_run 开头只取一次 now，各任务到期只跑一次、不补跑。
    被 OLED 占住 127ms 后，跟踪任务只补 1 刻而不是 12 刻，从 100Hz 掉到约 8Hz，
    步长 2.5 度/刻就成了 20 度/秒。

    【改法一：只刷变化的行】

        static char oled_line_cache[4][17];

        line = (uint8_t)(y / 16U);      <- 注意是除号，不是取模
        if (strcmp(oled_line_cache[line], buf) == 0) { return ; }
        memcpy(oled_line_cache[line], buf, 16);
        dev_oled_show_string(0, y, buf);

    【踩坑】第一次写成了 y % 16。y 只会是 0/16/32/48，取模永远是 0，
    四行共用 cache[0]，每行都在和上一行比，永远不相等 —— 缓存等于没写。
    这个错误不报错、不清屏、显示正常，只是优化没生效。改回 y / 16 才真正起作用。

    【改法二：整行一次发】

    SSD1306 页寻址模式下，每写一个数据字节列地址自动加一，
    所以不需要逐字重新定位，一行 128 字节可以一次发完。

        static uint8_t buf[129];        /* 0x40 + 128 字节 */
        buf[0] = 0x40;
        /* 组装 16 个字符的 8 字节字模到 buf[1..128] */
        dev_oled_write_cmd(0xB0 + page + half);
        dev_oled_write_cmd(0x00 | (x & 0x0F));
        dev_oled_write_cmd(0x10 | ((x >> 4) & 0x0F));
        HAL_I2C_Master_Transmit(&hi2c1, OLED_I2C_ADDR, buf, 129, 100);

    【对比】

        逐字节发送            1408 次/刷新   ~127ms   追光约 20 度/秒
        加行缓存（刷 1 行）     352 次        ~42ms    约 150 度/秒
        再整行合并写              8 次         ~6ms    接近 250 度/秒

    【改完要清理】dev_oled_show_char() 和 dev_oled_write_data() 没有调用点了，
    都是 static 函数，留着会报 -Wunused-function，要一起删。
    dev_oled_write_cmd() 还要用（dev_oled_clear 和新函数都在调）。

    【教训】"加缓存"这类优化必须用数字验证。慢的时候先调参数（步长、增益）
    只能得到线性改善；改善不明显，就说明是调度或阻塞问题，不是参数问题。

    【状态】已实机验证。整行合并后追光速度恢复正常，手电移动时云台随手就跟上，
    快速横扫也能跟住，不再有一顿一顿的感觉。

六、任务三：PWM 与舵机 dev_servo.c/h

-001  PWM 初始脉宽要设成中位

    CH1 和 CH4 的 Pulse 初始值都设为 1500（中位 1.5ms），
    这样上电时舵机不会乱转。

    【为什么】PWM 启动时比较寄存器的值决定第一个周期的脉宽。
    若为 0，舵机收到的是"持续低电平"的无效信号，会失去控制而抖动。

-002  整数除法的顺序

    angle/180 * 2000 整数除法，导致所有中间角度失效。
    应将除法与乘法调换位置。

    【正确写法】先乘后除，并把中间结果提升为 32 位：
        uint16_t pulse = 500 + (uint32_t)angle * 2000 / 180;


================================================================================
七、任务四：MPU6050 与姿态解算
================================================================================

-001  MPU6050：一颗芯片，两个传感器

    MPU6050 在单个芯片内集成了两个关键的 MEMS 传感器：

        三轴加速度计（Accelerometer）：
            测量加速度（包括重力）。静止时，它能通过测量重力在各轴的分量，
            算出物体的倾斜角度（俯仰/滚转）。优点是静态稳定，但运动时噪声大。

        三轴陀螺仪（Gyroscope）：
            测量角速度（旋转的快慢）。对角速度进行积分就能得到角度。
            优点是动态响应好，但静止时有漂移误差，随时间累积会越来越偏。

    核心特性与用法

        通信接口：通过 I2C 总线与 STM32 通信，最高速率 400kHz。
        设备地址：默认 0x68（当 AD0 引脚接地时），接高电平则变为 0x69。
        量程可配：加速度计可选 +/-2g 到 +/-16g，陀螺仪可选 +/-250 度/s 到 +/-2000 度/s。
                  本项目建议设为 +/-2g 和 +/-2000 度/s。
        内部 DMP：自带数字运动处理器，能直接输出姿态解算结果（四元数），
                  帮你省去大量计算。

    项目里怎么用

        GY-521 模块就是 MPU6050 的载体。任务四中两种方式获取姿态：

        软件解算（推荐学习）：读取原始加速度和角速度，自己用互补滤波融合。
            加速度计提供长期稳定的角度基准，陀螺仪提供快速动态响应，
            两者互补能有效克服各自缺陷。

        使用 DMP：调用官方库，让芯片直接输出四元数，再转为欧拉角。
            代码简单但依赖官方库，灵活性较低。

-002  任务四的核心链路

    读取 MPU6050 原始数据 -> 零位校准 -> 互补滤波解算姿态 -> 映射到云台两轴
    -> 模式二随动。全程软件解算，不依赖 DMP 库。

-003  数据流

    MPU6050 (I2C 0xD0)
        |
        v
    dev_mpu6050        读原始 ax/ay/az/gx/gy/gz
        |
        v
    attitude           减偏置 -> 加速度计解算角度 -> 互补滤波融合
        |              （调用 filter_comp_update）
        v
    gimbal             模式二下：姿态角映射到云台目标角
        |
        v
    dev_servo -> bsp_pwm -> 舵机


================================================================================
八、互补滤波与滑动平均 filter.c/h
================================================================================

-001  互补滤波把两者的优点结合起来：complementary（互补）

    最终角度 = alpha * (陀螺仪积分角度) + (1-alpha) * (加速度计角度)

    alpha 通常取 0.98，表示"信任陀螺仪 98%"。

    陀螺仪提供短期动态响应，加速度计提供长期稳定基准；两者互补，取长补短。

        加速度计：静止时准，一动就乱跳。
        陀螺仪：测量的是角速度，对角速度积分得到角度。动态平滑，
                但静止时角度会慢慢漂走。

        coef = 0.98：98% 信任陀螺仪，2% 信任加速度计。

    调参：

        姿态跟随有滞后 -> 减小 alpha（更信任加速度计）
        姿态抖动大     -> 增大 alpha（更信任陀螺仪）

-002  互补滤波的数学公式

    filter_comp_update 内部做的事：

        float dt = (now_tick - f->last_tick) / 1000.0f;   /* 秒 */
        f->last_tick = now_tick;

        /* 陀螺仪积分预测 + 加速度计修正 */
        f->angle = f->coef * (f->angle + gyro_rate * dt) + (1.0f - f->coef) * acc_angle;

-003  对互补滤波的总结

    互补滤波 = 加速度计（静态准）+ 陀螺仪（动态准）的加权融合。
    用陀螺仪提供短期平滑的动态响应，用加速度计提供长期稳定的角度基准，
    两者互补，得到又稳又准的姿态角。

-004  滑动平均滤波器（Moving Average Filter，MA）

    也叫移动平均滤波器，是最简单、最常用的 FIR 低通滤波器。
    核心思想是：当前输出 = 最近 N 个输入样本的算术平均值。

    实现要点：用 sum 维护"窗口内累加和"，每次更新只做"加上新样本、减去最旧样本"，
    不需要遍历整个窗口（O(1) 更新）。
    窗口未填满时按"已填样本数"取平均，这样开机第一个样本就能输出合理值，
    不会出现"从 0 慢慢爬升"。

-005  互补滤波系数从 0.98 降到 0.60：交叉频率的问题

    【现象】模式二反向翻转（抬起不超过 45 度后迅速放平），舵机先往原方向多走一点，
    然后转过头，最后慢慢修回来。动作越猛越明显。

    【排除过程】
        1. 前馈增益改 0        -> 现象还在，幅度小一些 => 前馈是叠加因素，不是主因
        2. 输出低通改 0        -> 现象还在，但动作变"陡" => 只抹 1 度台阶，不是回弹原因
        3. 互补滤波系数往大调   -> 现象加剧
        4. 往小调              -> 0.69 时已很小，最终定 0.60

    【根本原因】交叉频率太低。

    互补滤波是一个分界点：低频信加速度计（重力基准），高频信陀螺（积分）。

        f_c = (1 - alpha) / (2 * pi * dt)        dt = 20ms

        alpha    加速度计时间常数    交叉频率     手部动作(1~3Hz)由谁主导
        0.98     约 1000ms           约 0.16Hz    全部由陀螺积分
        0.85     约 133ms            约 1.2Hz     大部分由陀螺积分
        0.60     约 50ms             约 3.2Hz     主要由加速度计

    alpha=0.98 时交叉频率只有 0.16Hz，手的动作（1~3Hz）完全落在陀螺积分范围内。
    陀螺数字低通有 8.3ms 延迟，还有残余零偏，误差被完整积分进角度：
        - 反向瞬间陀螺还报原方向 -> 角度继续往原方向涨 -> 舵机先回弹一下
        - 停下后只有 2% 的加速度计在拉 -> 时间常数 1 秒 -> 回位极慢

    alpha=0.60 把交叉频率抬到 3.2Hz，手部动作落进加速度计的管辖范围，
    角度直接跟重力，陀螺的延迟和零偏不再累积，两个症状一起消失。

    【代价】alpha 越低，加速度计权重越大，对噪声和运动加速度越敏感。
    0.98 -> 0.60 等于把加速度计权重从 2% 提到 40%，所以不是越小越好。
    实测 0.60 时静止无可见抖动、快速平移也无假性偏转，因此没有再加速度计模长门控。

    【顺带】MPU6050_CONFIG 仍是 0x04（20Hz，延迟 8.3ms）。
    alpha 降下来后陀螺延迟影响已经很小，这一项不用再动。

    【教训】"参数往哪个方向调会变好"比现象本身更能定位问题。
    当时第一反应是"加速度计被运动加速度污染"，方向错了；
    把 alpha 调大反而加剧，才反过来指向陀螺积分。

================================================================================
十、MPU6050 驱动 dev_mpu6050.c/h
================================================================================

-001  核心架构：一颗芯片，两个传感器

    MPU6050 在单个芯片内集成了两个关键的 MEMS 传感器：

        三轴加速度计（Accelerometer）：测量加速度（包括重力）。
            静止时，它能通过测量重力在各轴的分量，算出物体的倾斜角度
            （俯仰/滚转）。优点是静态稳定，但运动时噪声大。

        三轴陀螺仪（Gyroscope）：测量角速度。
            对角速度进行积分就能得到角度。优点是动态响应好，
            但静止时有漂移误差，随时间累积会越来越偏。

        此外，芯片内部还有一个数字运动处理器（DMP），它是一个专用的小型处理器，
        可以独立完成复杂的姿态解算，直接输出稳定的姿态数据（如四元数），
        从而减轻主控 MCU 的运算负担。

-002  通信接口：I2C 总线

    MPU6050 通过 I2C 总线与 STM32 通信。

        通信速率：支持标准模式（100kHz）和快速模式（400kHz）。
                  为了满足项目中姿态解算 >=50Hz 的更新率要求，
                  建议配置为 400kHz，以提高数据读取速度。
        设备地址：默认 7 位地址是 0x68（当 AD0 引脚接地时）。
                  在 HAL 库编程中，需要将其左移一位，使用 8 位地址 0xD0。

-003  关键寄存器速查

    MPU6050 需要通过配置和读取一系列寄存器来驱动。
    以下是项目中最关键的几个寄存器：

        寄存器名称        地址(Hex)   功能说明
        ----------------------------------------------------------------------
        PWR_MGMT_1        0x6B        电源管理。写入 0x80 复位，写入 0x00 唤醒芯片。
        WHO_AM_I          0x75        设备 ID。地址正确时读取应返回 0x68，用于检测芯片是否存在。
        GYRO_CONFIG       0x1B        陀螺仪量程配置。设置角速度的满量程范围。
        ACCEL_CONFIG      0x1C        加速度计量程配置。设置加速度的满量程范围。
        CONFIG            0x1A        数字低通滤波器（DLPF）配置。用于滤除高频噪声。
        ACCEL_XOUT_H      0x3B        加速度数据起始地址。从这里连续读 6 字节，得到 X/Y/Z 三轴加速度。
        GYRO_XOUT_H       0x43        陀螺仪数据起始地址。从这里连续读 6 字节，得到 X/Y/Z 三轴角速度。

-004  数据格式与量程换算

    MPU6050 输出的原始数据是 16 位带符号整数（int16_t）。
    每个轴的数据由高 8 位和低 8 位两个寄存器组成，需要将它们组合起来：

        int16_t accel_x = (int16_t)(buffer[0] << 8 | buffer[1]);

    组合后的数值需要根据配置的量程换算成有物理意义的单位。
    为了获得最佳精度，本项目采用以下配置：

        陀螺仪量程：配置为 +/-2000 度/s（FS_SEL=3）。对应的灵敏度为 16.4 LSB/(度/s)。
                    换算公式：角速度(度/s) = 原始值 / 16.4

        加速度计量程：配置为 +/-2g（AFS_SEL=0）。对应的灵敏度为 16384 LSB/g。
                      换算公式：加速度(g) = 原始值 / 16384

-005  姿态解算：从原始数据到稳定角度

    无法直接使用原始的加速度或角速度数据来驱动云台，因为各有缺陷。
    正确的做法是使用互补滤波算法将它们融合。

        零位校准：上电后保持传感器静止，采集数百组数据求平均，作为零位偏置。
                  后续每次读取数据时都减去这个偏置，以消除静态误差。

        互补滤波融合：将加速度计解算出的角度（长期稳定但动态噪声大）
                      和陀螺仪积分出的角度（动态响应好但会漂移）进行加权融合。

        核心公式：最终角度 = alpha * (陀螺仪积分角度) + (1-alpha) * (加速度计角度)

        系数 alpha：通常取 0.98，表示"信任陀螺仪 98%"。
                陀螺仪提供短期平滑的动态响应，加速度计提供长期稳定的基准，
                从而互相修正彼此的缺陷。

        更新率保障：项目要求姿态更新率不低于 50Hz。
                    这意味着要确保在 app_task 中，logic_attitude_task() 的调用周期
                    不超过 20ms。

-006  上电流程的注意事项

    复位后必须延时 100ms，否则后续配置写入无效。
    原因：芯片复位需要时间，复位后立即写寄存器会被忽略。

    WHO_AM_I 校验可以确认设备和地址正确。
    量程配置后，attitude 层才能正确换算单位。

-007  寄存器地址连续，一次读 14 字节

    MPU6050 的寄存器地址是连续的，从 ACCEL_XOUT_H (0x3B) 开始一次读 14 字节，
    已经包含了 GYRO_XOUT_H (0x43)，不需要单独去读。

        寄存器          地址    数据
        ------------------------------------
        ACCEL_XOUT_H    0x3B    ax 高字节
        ACCEL_XOUT_L    0x3C    ax 低字节
        ACCEL_YOUT_H    0x3D    ay 高字节
        ACCEL_YOUT_L    0x3E    ay 低字节
        ACCEL_ZOUT_H    0x3F    az 高字节
        ACCEL_ZOUT_L    0x40    az 低字节
        TEMP_OUT_H      0x41    温度高字节
        TEMP_OUT_L      0x42    温度低字节
        GYRO_XOUT_H     0x43    gx 高字节
        GYRO_XOUT_L     0x44    gx 低字节
        GYRO_YOUT_H     0x45    gy 高字节
        GYRO_YOUT_L     0x46    gy 低字节
        GYRO_ZOUT_H     0x47    gz 高字节
        GYRO_ZOUT_L     0x48    gz 低字节

十一、姿态层 attitude.c/h

-001  灵敏度的含义

    float ax = (raw.ax - offset.ax) / 16384.0f;

    16384 类似于灵敏度，指 1g 对应 16384.0 数字量。
    1rad 约等于 57.2958 度。

-002  16384 是怎么算出来的

    int16_t 共 65536 个刻度；+/-2g 一共是 4 个单位，
    单位 g = 65536 / 4 = 16384。其余量程类似。

    【补充】+/-2000 度/s 量程：65536 / 4000 = 16.4，即 16.4 LSB/(度/s)。

十二、云台映射 gimbal.c/h

-001  符号方向需要实测确定

    映射公式里的 + / - 取决于 MPU6050 安装朝向和云台机械结构。
    先按下面写，实测：

        操作                       期望现象                如果反了
        -----------------------------------------------------------------------
        姿态板上仰（pitch > 0）    云台俯仰轴跟随上仰      把 90 + pitch 改成 90 - pitch
        姿态板右滚（roll > 0）     云台方位轴跟随右转      把 90 - roll 改成 90 + roll

    先把映射写上去，实测再调符号，调好的符号写入开发报告。

-002  [重点] 恢复机制会阻塞主循环（attention）

    gimbal.c 里每 5 秒尝试恢复 MPU6050，logic_attitude_init 内部有：

        HAL_Delay(500);              /* 500ms */
        dev_mpu6050_calibrate();     /* 100 次 * 5ms = 500ms */

    总共阻塞约 1 秒。

    【权衡】非阻塞化需要较大的代码改动，而 5 秒的恢复间隔对用户体验影响可接受。

-003  MPU6050 只在模式二下被读取

    gimbal.c 的 logic_gimbal_task 只在模式二下调 logic_attitude_task。
    模式一、三下 MPU6050 不被读取，运行中故障只在切换到模式二时才被发现。

    这是设计选择，不是 bug。

-004  [重点] 极端航向角下姿态解算失效（欧拉角奇异点）

    【现象】
    姿态板航向角转到接近 +/-90 度时，此时轻轻往上下一转，
    pitch 读数就会加速变大或变小（不是缓慢漂移，是加速偏离）。

    【排查过程】
    一开始怀疑是 MPU6050 在极端姿态下数据异常，或者是前馈项在
    大角度时被放大。检查后发现数据本身正常，问题出在解算公式本身。

    【根本原因】
    attitude.c 里用的是两条互相独立的二维公式：

        acc_pitch = atan2f(ay, az);
        acc_roll  = atan2f(ax, az);

    这两条公式只在"航向角为 0 附近"才近似成立，因为：

        pitch 用的是 Y、Z 分量  ->  绕 Z 轴（航向）转到 +/-90 度时失效
        roll  用的是 X、Z 分量  ->  绕 Z 轴转到 0 度时失效

    也就是说，两者在"绕 Z 轴旋转"这一维度上重叠、互相干扰，
    这就是欧拉角在 +/-90 度附近的奇异点（万向节死锁的数学本质）。

    更根本的限制是：加速度计只能测出重力方向，无法分辨
    "绕重力轴转了多少"，所以纯加速度计解算在航向维度上是没有基准的。

    正反馈过程（这解释了为什么是"加速偏离"而不是缓慢漂移）：

        roll 读数漂移  ->  驱动方位轴转动
          ->  姿态板的航向角进一步偏离  ->  pitch/roll 耦合更严重
          ->  roll 读数漂移更大  ->  循环加剧

    【解决方式】
    承认这是纯加速度计解算的固有局限，在软件上加保护切断正反馈：

        #define GIMBAL_TILT_LIMIT_DEG   55.0f
        /* 姿态板总倾角（与航向无关）超过 55 度时，冻结方位轴 */

    触发条件用"总倾角"而不是 pitch：

        tilt_total = acosf(az / sqrtf(ax*ax+ay*ay+az*az))

    因为这个量只跟重力方向有关，在航向旋转下不变，
    所以判断"是否已进入耦合区"是可靠的。

    考核题要求的工作范围是 +/-45 度，在保护阈值 55 度以内，不影响验收。

    【教训】
    1) 用欧拉角做姿态解算，必须清楚它的有效范围。
       pitch/roll 两条独立的 atan2 公式只在水平姿态附近成立，
       一旦涉及大角度航向旋转就会耦合。
    2) 遇到"读数加速偏离"要优先怀疑正反馈（传感器 -> 执行器 -> 姿态变化
       -> 传感器），而不是怀疑传感器本身故障。
    3) 纯加速度计没有航向基准，这是物理限制不是代码 bug。
       要全范围可用必须引入磁力计，或改用四元数/旋转矩阵的三维姿态解算。
       本项目选择"限制工作范围 + 软件保护"，是成本与收益权衡后的决定。

-005  故障恢复机制设计说明

    故障概率：MPU6050 和 I2C 总线在正常工作条件下故障概率极低。

    恢复策略：进入模式二后，若检测到 MPU6050 异常，每 5 秒
              调用一次 logic_attitude_init() 尝试重新初始化。

    代价：logic_attitude_init() 内部有 HAL_Delay(500) 和
          100 次校准采样（约 500ms），共阻塞主循环约 1 秒。

    权衡：非阻塞化需要较大的代码改动（把延时拆成状态机），
          对整体架构影响大。考虑到故障概率低、恢复间隔 5 秒，
          1 秒阻塞对用户体验影响可接受。

    改进方向：若后续需支持更高实时性，可把校准过程改为非阻塞状态机，
              或把恢复机制放到独立低优先级任务中。

-006  [重点] 踩坑记录：跟随滞后，最后靠"前馈"而不是"滤波"解决

     【现象】
     模式二下转动手持板子，云台跟随的滞后感很明显，
     想要的是"跟着手快速平滑运动"的手感。

     【排查过程】
     一开始以为"滞后 = 滤波太强"，于是沿着滤波这条线一路调：

         20ms 更新 + alpha=0.98   ->  时间常数约 1 秒，慢得明显
         改成 10ms 更新        ->  好一些，但抖动变大
         alpha 从 0.95 一路降到 0.78
         又给舵机输出加滑动平均（窗口 4）
         又加一级慢低通（系数 0.35）

     结果响应虽然快了，但舵机变成"一步一卡"，
     而且总滞后越加越大----最后算下来超过 300ms，比一开始还肉。

     【根本原因】
     我把"跟手"和"平滑"当成同一件事在调，方向就错了：

         alpha 调小 -> 姿态角跟手了，但噪声被放行 -> 舵机抖
         再加输出平滑 -> 抖被压住了，但滞后被叠上去 -> 又变肉

     这是一条死循环：每解决一个问题，就制造另一个问题。

     真正的原因是：**反馈控制永远滞后**。
     纯反馈是"先看到偏差，再去修正"，无论怎么调滤波系数，
     都只能在这个前提下折中，无法同时做到"快"和"稳"。

     【解决方式】
     换成"前馈 + 反馈"的结构。关键认识是：

         陀螺仪测的就是手转多快 -> 可以直接用来预测目标在哪

         原来：目标角 = 融合角度                      （总是慢半拍）
         改成：目标角 = 融合角度 + 前馈增益 * 角速度   （提前）

     预设参数：

         互补滤波系数  alpha = 0.85
         前馈增益      GIMBAL_FEEDFORWARD_GAIN = 0.06
         输出低通系数  GIMBAL_SERVO_LPF_COEF   = 0.75（只负责抹掉取整台阶）
         滑动平均      删除

     总滞后估算：从约 300ms 降到 50ms 以内。

     【体会与教训】
     1) "跟手"（响应速度）和"平滑"（噪声抑制）是两个独立指标，
        要用两种不同的手段分别解决：

            平滑 -> 互补滤波 + 输出低通（会带来滞后，只能少量使用）
            跟手 -> 前馈（不带来滞后，反而抵消已有滞后）

        混在一起调，就会陷入"调快->变抖->加平滑->又变肉"的死循环。

     2) 前馈是"预测"，不需要等误差出现就能提前动作。
        凡是"传感器能直接测出被控量变化率"的场合，都可以考虑前馈：
        本项目的陀螺仪正好直接给出角速度，是天然的前馈信号源。

     3) 前馈也有代价：增益太大时会过冲甚至自激振荡。
        所以增益要从小往大试（先 0.06，范围 0.03~0.12），
        而且一次只改一个参数。

     4) 排查时的教训：换方向要比在原方向上死磕更有效。
        我在滤波系数上折腾了 alpha=0.98->0.78 好几轮，都在同一个思路上；
        一旦换成"前馈"这个新结构，问题是直接消失的。

     【上板验证要点】
         0.06 下：跟手且不冲       -> 保持
         还嫌慢                    -> 0.08 -> 0.10
         先冲过头再回来（过冲）    -> 0.04
         静止时自己抖或画圈（自激）-> 0.03 或更低
     如果某个轴方向反了，就把该轴的前馈符号取反，一次只改一个轴。


================================================================================
十三、ADC 与 DMA bsp_adc.c/h
================================================================================

-001  ADC 基本参数

    STM32F103 的 ADC 是 12 位，输出范围 0~4095。

        电压        数字值
        -----------------------
        0V          0
        1.65V       2048（约一半）
        3.3V        4095

        换算：U = value * 3.3V / 4095

-002  采样过程

    ADC 内部有一个逐次逼近寄存器，采样时：

        采样保持电路把输入电压"冻结"住
        逐次逼近，从最高位开始比较，12 次比较后得到 12 位结果
        结果存入数据寄存器

    这个过程需要时间，所以 ADC 有采样时间配置。
    采样时间越长，精度越高，但转换越慢。

-003  扫描模式

    STM32 的 ADC 支持扫描模式：

        按配置的顺序，依次转换 IN1、IN2、IN3、IN4
        每转换完一个通道，结果存入数据寄存器
        全部转换完后，可以触发中断或 DMA

    CubeMX 里添加通道的顺序决定转换顺序，
    比如按 IN1->IN2->IN3->IN4 添加，那转换顺序就是 PA1->PA2->PA3->PA4。

-004  连续转换模式

        单次模式：转换一次就停，需要手动触发下一次
        连续模式：转换完自动开始下一轮，一直转

    追光采样用连续模式，让 ADC 持续更新数据，DMA 持续搬运。

-005  DMA：直接存储器访问

    如果不用 DMA，ADC 每转换完一个通道，CPU 要：

        读 ADC 数据寄存器
        存入数组
        清标志位
        准备下一次转换

    4 路 ADC 每 50ms 采样一轮，CPU 频繁被打断，影响其他任务。
    DMA 的作用就是让硬件自动搬运数据，不占 CPU。

-006  本项目中 DMA 的工作流程

        ADC 转换完 IN1，DMA 把数据寄存器搬到 adc_dma_buf[0]
        ADC 转换完 IN2，DMA 搬到 adc_dma_buf[1]
        ADC 转换完 IN3，DMA 搬到 adc_dma_buf[2]
        ADC 转换完 IN4，DMA 搬到 adc_dma_buf[3]
        如果是循环模式，回到第 1 步继续

    CPU 全程不需要参与，它只管在需要的时候读 adc_dma_buf 数组。

    读取时不需要停 DMA，直接拷贝当前值即可。虽然 DMA 在同时更新 adc_dma_buf，
    但 uint16_t 的读写是原子的（16 位可以被 CPU 一次读完），不会读到半截数据。

-007  为什么不用中断

    如果用 ADC 中断，每转换完一个通道就要进一次中断，4 路就是 4 次中断，
    再加上主循环调度，开销大。

    DMA 方式下，CPU 只在需要时读一次数组，其他时间完全不管，效率最高。

-008  memcpy 用法

        memcpy(buf, adc_dma_buf, sizeof(adc_dma_buf));

-009  [重点] 上板验证要点（attention）

    照单一光敏，看那一路读数是否明显、单调上升；
    同时其它三路基本不变。
    如果被照那路上升但相邻路也跟着变，就是采样时间不够，
    4 路都改成 71.5 或 239.5 周期。

-010  [重点] 四路读数与物理方位的对应（实测确定，以此为准）

     【关键结论】数组下标由 ADC 的"转换次序（Rank）"决定，不由通道号决定。
     因此 CubeMX 里 Rank 的填写顺序必须与接线、与软件下标宏三者严格一致。

     【光敏模块的物理布局：四角，正放】

     板子正放（不再斜放），四只光敏落在板子的四个角上。
     从右上角起顺时针，丝印依次是 A1、A2、A3、A4：

              +-----------------------+
              | A4                 A1 |
              |                       |      A1 右上    A4 左上
              |                       |      A2 右下    A3 左下
              | A3                 A2 |
              +-----------------------+

     【实际接线表（已实测确认，接线没有随布局改变）】

         物理位置   丝印    网络名    引脚     ADC 通道     数组下标
         -------------------------------------------------------------
          右上      A1     ADC_U    PA3     ADC1_IN3      [2]
          右下      A2     ADC_R    PA1     ADC1_IN1      [0]
          左下      A3     ADC_D    PA4     ADC1_IN4      [3]
          左上      A4     ADC_L    PA2     ADC1_IN2      [1]

     注意：网络名是当初按"上右下左"的十字布局起的，现在物理位置变成四角，
     网络名已经名不副实，但对算法没有影响 —— 算法只看数组下标。

     【配对方式：同侧两只取平均，合成虚拟的上下左右】

         LT = track_level[TRACK_INDEX_LT] = [1] = A4   左上
         RT = track_level[TRACK_INDEX_RT] = [2] = A1   右上
         LB = track_level[TRACK_INDEX_LB] = [3] = A3   左下
         RB = track_level[TRACK_INDEX_RB] = [0] = A2   右下

         左 = (LT + LB) * 0.5f        右 = (RT + RB) * 0.5f
         上 = (LT + RT) * 0.5f        下 = (LB + RB) * 0.5f

         total   = LT + RT + LB + RB        合成后总量不变，仍等于四路之和
         diff_lr = 左 - 右                  大于 0 表示左侧更亮
         diff_ud = 上 - 下                  大于 0 表示上方更亮

     两条虚拟连线互相垂直，两个轴天然解耦。
     而且每路都是两只取平均，单只光敏的增益离散、老化、局部遮挡会被摊平一半。

     【走过的弯路：两种都别踩】

     1. 相邻配对（对角）。曾经按顺时针顺位接成 A1->PA1、A2->PA2、A3->PA3、A4->PA4，
        于是 [0][1] 是 A1(上)+A2(右)、[2][3] 是 A3(下)+A4(左)，两条连线都成 45 度，
        测不出干净的水平 / 垂直分量，表现为光源移到侧面时四路读数差距很小，云台不动或绕圈。

     2. 斜放 45 度取对面两只。能得到水平与竖直两组读数，但斜放的支架不好固定。

     现在的做法是"正放 + 同侧平均"，把上面两个缺点都避开了。

     【实测验证方法】

     模式三那一行按 左上 右上 左下 右下 显示，关灯、手电筒与模块等高、距离 1m：

         移到【正右方 30 度】 -> 右上(A1) 与 右下(A2) 同时变大，左侧两路变小
         移到【正上方 30 度】 -> 左上(A4) 与 右上(A1) 同时变大，下排两路变小

     如果两个方向都影响两排，说明还有耦合（见十四 -008 关于读数反相的说明）。

     【附带发现】这只模块的读数是反相的：光弱读数大、光强读数小。
     判断"有没有光"时要注意方向，详见十四 -008。


================================================================================
十四、任务五：自动追光 track.c/h
================================================================================

-001  一句话算法

    看左右哪边亮，就往哪边转一点点；转一点点之后再看一次。
    差异小到"环境亮度的 2%"以内，就停下（考核给的是 10%，实测收紧）。

-002  对"对准 / 未对准"的判断：引入"对准可信度"

    方案：引入 track_align_ticks 这个"对准可信度"的积分量。

        - 需要连续 15 tick 落在容差内才算对准
        - 需要连续 5  tick 落在容差外才能算作未对准
        - 如果偏差过大：track_align_ticks 归零，直接算作未对准

    为什么两边不对称：
        不能轻易认定对准，且要果断判定未对准。

-003  归一化的作用

    (-1.0) * (left_right_diff / diff_scale) * 6.0

    将偏差度归一化，使其变成 (-1, 1) 的系数，方便乘以放大系数。

-004  四舍五入到整数的一种方法

        float num = xxxxx...;
        x = (uint8_t)(num + 0.5);

    小数部分大于 0.5 累加后会大于一、被截断；
    小于 0.5 则会被直接截断。

    【为什么需要】舵机接口只收整数角度。若内部也用整数累加，
    小于 1 度的步进（比如 1.5 度）会被丢掉，表现为"总是差一点对不准"。
    所以内部用 float 累加，只在下发时四舍五入。

-005  [重点] 上板调试：只需动两个地方

    1. 方向反了

       云台反转：只改 track.c 顶部的符号，不用碰任何算法：

           #define TRACK_YAW_DIRECTION      (-1.0f)    /* 反了 -> 改成 (+1.0f) */
           #define TRACK_PITCH_DIRECTION    (-1.0f)    /* 反了 -> 改成 (+1.0f) */

    2. 太抖或者太慢的改法

        现象                     改哪个                如何改
        ----------------------------------------------------------------------
        到位后还在小幅来回摆     TRACK_MA_WIN          8 -> 12（平滑更强）
        还是摆                   TRACK_STEP_*_DEG      1.5 -> 1.0（步子更小）
        反应太慢，追不上         TRACK_STEP_*_DEG      1.5 -> 2.5（步子更大）
        总是"差一点对不准"       TRACK_TOL_RATIO       0.10 -> 0.15（容差放宽）
        没对准就报 ON            TRACK_TOL_RATIO       0.10 -> 0.06（容差收紧）
        正常光照却误判"无光"     TRACK_TOTAL_LEVEL_MIN 16000 -> 调大（上限 16380）

-006  为什么必须用"相对容差"而不是固定阈值

    设环境整体变亮 k 倍，四路读数同时变为 k 倍，总量变为 k 倍，
    容差（= 总量 * 10%）也变为 k 倍，
    而"差异与容差的比值"保持不变，所以判定结果与绝对亮度无关。

    对比：若用固定阈值（例如差异 > 100），环境变暗后差异可能永远达不到 100，
    判据就失效了，必须重新标定。

-007  无定向光源与全黑的判据

    主判据（相对）：各路读数彼此接近，即差异小于相对容差。
                    此时既可视为已正对光源，也可视为无定向光源。

    保护性判据（总量上限）：这只模块的读数是反相的 —— 光越弱读数越大，
                            光越强读数越小。所以"没有光"对应的是四路之和
                            接近满值（4 x 4095 = 16380），而不是偏小。
                            代码里当四路之和超过 16000 时判为完全无光，
                            云台保持静止，防止噪声驱动乱转。

                            不是"下限"：光太强时读数被压到低端、总量偏小，
                            那属于"太亮"而不是"没光"。

                            该判据只回答"有没有光"，不参与"光在哪边"，
                            因此不违反"不得使用固定绝对阈值"的要求。

-008  追光靠太近会持续摆动：三次猜测和真正的根因

    【现象】

    手电靠近到十几厘米，云台在目标附近持续来回摆，幅度 10~20 度，
    状态栏一直显示"追光中"；换手机、换台灯一样，拉开到 0.5 米以上正常。

    【猜测一：灯不一样（错）】

    曾归因于手电筒个体差异：亮度饱和、光斑太宽、双灯珠。
    改对光照参数后重测发现，真正的自变量是距离，不是灯。

    【猜测二：信噪比不足（错）】

    判据是"差值 < 2% 总量"，近距离总量小、容差跟着小，
    可能已经和测量抖动同量级。

    但实测推翻：晃动时四路读数并不乱跳，差值也是稳的 —— 测量没问题。
    顺着这个思路还给容差加过"测量不确定度"兜底（均方根合成 6 个计数），
    实测无效，已回退。

    【猜测三：控制律（对）】

    关键对照实验：光源固定不动，用手把云台左右各转 10 度。
    四路读数明显变化（一路 25 -> 35 或 15）
    -> 近距离传感器仍有分辨力，不是"看不见方向"。

    那就只剩控制律。两个数一乘就清楚了：

        测量过 8 刻滑动平均   ->  等效滞后约 4 刻
        每刻步长固定 1.5 度
        -> 意识到该停之前还会多走 4~8 步，即 6~12 度
        而近距离容差带在角度上只有约 1 度

    于是每走一步都冲出带子，下一步用滞后的测量看到反向偏差又走回来，
    形成 10~20 度的极限环。

    【验证】

        限步 1.5 度 -> 0.3 度：立刻稳住
        限步 0.5 度：又开始摆

    临界值落在 0.3~0.5 之间，和"步长 × 滞后 < 带子宽度"的估算
    （0.25~0.3 度）吻合。

    【修复：步长随总量自适应】

    固定 0.3 度能稳但太慢（30 度每秒，45 度要 1.5 秒）。
    远处容差带在角度上宽得多，本可以用大步，于是让步长跟着总量走：

        #define TRACK_STEP_REF_LEVEL   4200.0f   /* 总量为此值时 */
        #define TRACK_STEP_REF_DEG     0.4f      /* 步长取 0.4 度 */
        #define TRACK_STEP_LIMIT_DEG   1.5f      /* 封顶，大行程用 */

        float step_mag = TRACK_STEP_REF_DEG * (level_sum / TRACK_STEP_REF_LEVEL);

    近处小步不摆，远处大步不慢；45 度行程从 1.5 秒降到 0.3 秒。
    这套写法没有"距离判断"分支，因为总量本身随距离单调变化，
    天然就是距离的代理量。

    【为什么之前调容差、调滤波都没用】

    那些改的是"判据的宽严"，而病根在"动作的幅度"。两件事。

    【经验】

    回路里有滞后时，步长必须和滞后匹配：
        "每步走多远 × 滞后几拍 = 刹车距离"，
    刹车距离要小于目标区间的宽度，否则一定冲过头。

-002  [重点] delay 模块说明（已实现但当前未使用的通用工具）

     【为什么会有这个模块】

     项目里凡是"隔一段时间做一次"的逻辑，都不应该用 HAL_Delay()。
     例如：

         上电自检要亮 3 轮灯           需要 600ms
         按键消抖要等                   20ms
         LED 要每                       500ms 翻转一次
         OLED 要每                      100ms 刷新
         追光要每                       20ms 算一次

     如果用 HAL_Delay(600) 做自检，这 600ms 里主循环完全停住：
     串口收到的字节积压在环形缓冲里、按键按了没反应，
     而且会破坏所有基于"时间差比较"的周期调度。

     考核题也明确要求：显示刷新不应影响串口接收与按键响应。

     所以项目统一采用"非阻塞"的做法，在 app_task.c 里用
     HAL_GetTick() 的时间差比较来实现周期调度：

         if (now - last_tick >= INTERVAL) { last_tick = now; 做一次 }

     delay 模块就是把这种"一次性延时"的写法封装成可复用的结构体，
     放在 Utils 层作为通用工具。

     【提供的能力】

     delay_t 结构体：
         start_tick   启动时刻的时间戳
         interval_ms  延时长度（毫秒）
         running      1=计时中，0=已停止/未启动

     四个接口：

         void delay_start(delay_t *d, uint32_t interval_ms);
             启动一次性延时。对参数做题：d 为 0 或 interval_ms 为 0 时直接返回。
             正在运行时重新启动会覆盖之前的计时。

         uint8_t delay_is_expired(delay_t *d);
             查询是否到期。返回 1 表示已到期【并且自动停止】，
             后续再查询返回 0 ---- 这是"一次性"语义，保证只触发一次。

         uint8_t delay_is_running(delay_t *d);
             查询是否还在计时中。

         void delay_cancel(delay_t *d);
             取消延时。注意只清 running 和 start_tick，
             不清 interval_ms（保留原设定值便于调试查看）。

     【两个设计要点】

     1) 时间戳用减法比较，而不是直接比大小：

            if ((now - d->start_tick) >= d->interval_ms)

        这样能自动处理 uint32_t 溢出（HAL_GetTick 约 49.7 天回绕一次），
        不需要额外的溢出判断。这也是本模块头文件里特意说明的一点。

     2) 到期后自动停止（running 置 0）。
        这是"一次性延时"与"周期定时"的关键区别：
        一次性延时用来等一个事件到来（"再过 200ms 就做某事"），
        触发一次后就应该失效；
        而周期任务用 app_task.c 里的时间差比较，不需要 delay 模块。

     【当前状态：已实现，但全工程没有调用处】

     已确认：delay_start / delay_is_expired / delay_is_running / delay_cancel
     四个接口在整个工程中都没有被调用。

     原因是：现有需求用 app_task.c 里"手写时间差比较"的方式已经足够。
     五个周期任务（按键 10ms、LED 50ms、OLED 100ms、舵机 10ms、追光 20ms）
     都是周期性触发，不需要"启动一次性延时"这种语义。

     【为什么保留而不是删除】

     1) 它是一个自洽、有完整文档、经过设计的通用工具，
        删除会使 Utils 层失去一个可复用的基础件。

     2) 后续确实有会用到它的场景：
        - 串口"空闲若干毫秒认为一帧结束"的超时判断
        - OLED 的"提示信息显示 2 秒后自动消失"
        - 按键的长按判定改成事件驱动
        这些场景都是"某个事件之后等一段时间"，正好是一次性延时的用途。

     3) 保留并在文档中说明定位，比留一个没有解释的文件更好。
        一个"有明确设计意图但暂未接入"的模块是架构储备；
        一个"没人知道干什么用"的文件才是垃圾代码。

     【如果后续要接入，三个注意事项】

     - delay_t 实例必须定义在 .c 文件里（static），不要放在栈上，
       因为它的状态需要跨调用保持。
     - 不要在中断里调用，HAL_GetTick() 在中断里读到的值可能不是最新的。
     - 一次性延时的语义是"到期后自动失效"。
       如果需要"每隔 N 毫秒触发一次"，应该用 app_task.c 的周期调度写法，
       不要用 delay 模块反复 delay_start。

-101  MPU6050 恢复机制的 1 秒阻塞

    现象：模式二下每 5 秒重试一次恢复，每次阻塞约 1 秒。

    原因：logic_attitude_init() 内部有 HAL_Delay(500) 加 100 次校准采样
          （约 500ms），合计约 1 秒。

    取舍：非阻塞化需要把延时和校准拆成状态机，改动面较大；
          而 MPU6050 故障概率低、恢复间隔有 5 秒，
          所以选择接受这 1 秒阻塞。完整分析见 十二-002 与 十二-004。

    若后续要提高实时性：把校准过程改为非阻塞状态机，
          或把恢复机制放到独立低优先级任务里。

-102  MPU6050 只在模式二下被读取

    现象：运行中发生的 MPU6050 故障，只在切换到模式二时才被发现。

    原因：logic_attitude_task() 只在 logic_gimbal_task() 内部被调用，
          而后者只在模式二下执行。

    取舍：模式一和模式三都不需要姿态数据，按需读取可以省下每周期约
          14 字节的 I2C 传输，避免无谓占用主循环。所以这是有意为之。
          详见 十二-003。

-103  Core/Src/main.c 保持 CubeMX 生成的 2 空格缩进

    全项目 User/ 目录统一用制表符缩进，但 main.c 例外。
    原因是该文件由 CubeMX 生成，一旦在图形界面里改配置就会重新生成，
    手改的缩进会被覆盖；而且它的 MX_XXX_Init() 系列函数本身就带
    2 空格风格。所以刻意不去统一它，避免制造无意义的差异。
